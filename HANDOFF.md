This immediately found a real, previously-undocumented, High-severity defect (`FINDINGS.md` #18): 15 concurrent `POST /api/patient` requests race on `PatientService::insert()`'s unguarded `MAX(pid)+1` read, and most of them silently fail while still reporting `200` (the losing request's `MySqlException` from the DB's own real unique-index rejection is swallowed by the same "global error handler never overrides the default 200" bug already known from the Document `path` finding). A companion DB-layer test confirms the unique index itself is a genuine, working guard, independent of the PHP layer — the app's handling of the collision is what's broken, not the absence of a DB-level constraint. Two further races (`FINDINGS.md` #19) confirmed the same "reports success regardless of what happened" pattern already known from Message (`FINDINGS.md` #1/#3) also produces a real lost-update race under concurrent `PUT`s to one message id, and that concurrent `DELETE`s of the same appointment id all report success identically. All 4 new tests were run 4 times each against the live instance with no flakiness before being considered done; full `dotnet test OpenEmr.Tests.sln` passed 125/125 (up from 121).

A fifth grey-area test followed the same day, targeting Patient Insurance's already-known destructive-overwrite `PUT` (`FINDINGS.md` #4): 5 concurrent single-field `PUT`s to the same insurance record all report `200`, but only whichever request's write physically commits last survives — the other 4 callers' updates, including ones that briefly succeeded, are silently erased with no error to anyone (`FINDINGS.md` #20, High severity — a real multi-user data-loss risk, e.g. billing and front-desk staff editing the same patient's insurance record at the same moment). One iteration snag worth noting for future grey-area work: the first version of this test used a formulaic marker string for every raced field, which failed validation on `subscriber_state` specifically (`ListOptionRule::INVALID_LIST_OPTION` — that field is constrained to a real state-code list, unlike the other free-text subscriber fields exercised here) with a clean `400`, breaking the "all requests return 200" assertion; fixed by using a real state code for that one field's race value. Confirmed passing 5 consecutive runs with no flakiness after the fix; full `dotnet test OpenEmr.Tests.sln` passed 126/126.

A sixth grey-area test, same day: concurrent Practitioner creates sharing an identical username (`FINDINGS.md` #21, Medium severity) — a deliberately different flavor from the first five, since `users.username` has no uniqueness guard at any layer (DB or app), so this one never fails at all: 5 concurrent `POST /api/practitioner` calls with the same username reliably all return `201` with distinct real ids, every time. A second iteration snag, more consequential than the first: the initial version of this test had no cleanup, and its leaked shared-username fixture rows permanently broke the pre-existing `UsersDbTests.Users_Table_Has_No_Duplicate_Populated_Usernames` DB test on every subsequent run (caught immediately by running the full suite, not just the new test in isolation — a good reminder to always do that after adding a grey-area test, since these are exactly the kind of test that can poison shared table state other tests assert against). Fixed by adding a `finally`-block cleanup deleting the shared-username rows after assertions, the same pattern `ProcedureApiTests` already established for its intentionally-orphaned row; the already-leaked rows from the unfixed first run were purged manually via direct SQL. Confirmed 3 consecutive full-suite runs clean after the fix; `dotnet test OpenEmr.Tests.sln` passes 127/127.

## Environment — How To Stand It Up

```
cd docker
docker compose up -d
docker compose ps
```

Wait for both `mariadb` and `openemr` to show `healthy` — first boot after a volume reset takes several minutes (schema install + Apache startup), not seconds, and the `openemr` container can report `unhealthy` for 2-6 minutes before flipping to `healthy`. This is normal (confirmed via container logs — it's still running its own setup script, not crashing); poll past the first `unhealthy` reading rather than treating it as a failure.

**No manual first-login browser steps are actually required before the test suites pass** — confirmed this session by reading `LoginPage.ts` (`loginAs()` already calls `dismissRegistrationModalIfPresent()`, which clicks "Ask again later" on the product-registration modal automatically) and by the fact that CI (`run-suite.yml`) has always started from a bare fresh `docker compose up -d` with zero manual steps and passed. `docker-compose.yml`'s `OPENEMR_SETTING_rest_api`/`OPENEMR_SETTING_rest_fhir_api`/`OPENEMR_SETTING_oauth_password_grant` env vars already cover the Administration → Config → Connectors settings a human would otherwise click through. `node docker/reset-env.mjs` resets to a fresh volume and polls to healthy — nothing further is needed before running the suites.

If exploring the app manually in a browser (`https://localhost:9300`, `admin`/`pass`) rather than running the automated suites, the product registration prompt will still appear on first login (dismiss it, no effect on tests either way).

Then:

```
cd ../tests
dotnet restore OpenEmr.Tests.sln
dotnet test OpenEmr.Tests.sln
```

For the UI layer:

```
cd ../ui
npm install
npx playwright install
npx playwright test
```
