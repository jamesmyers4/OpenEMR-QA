Summary, roughly most-to-least severe:

- **`FINDINGS.md` #18 (High)** — `tests/OpenEmr.Api.Tests/GreyArea/ConcurrencyApiTests.cs`: 15 concurrent `POST /api/patient` requests race on `PatientService::insert()`'s unguarded `MAX(pid)+1` read; most silently fail while still reporting `200` (the DB's own real unique-index rejection is swallowed by the same "global error handler never overrides the default 200" bug already known from the Document `path` finding). A companion DB-layer test (`tests/OpenEmr.Db.Tests/GreyArea/ConcurrencyDbTests.cs`) independently confirms the unique index itself is a genuine, working guard — the app's *handling* of the collision is what's broken, not the DB layer.
- **`FINDINGS.md` #22 (High)** — `ui/tests/admin-duplicate-merge-race.spec.ts`: the classic-UI patient-merge flow (`merge_patients.php`) has zero locking around its destructive per-table delete/update loop. Two concurrent submissions of the identical merge both report `200`/"Merge complete.", each having physically executed a different, non-deterministic split of the real deletions. The first grey-area test built against the UI/session layer (Playwright's `context.request` sharing the admin session's cookies, not a bearer token or a second tab) rather than the API/DB layers; `mergeRows()`'s more complex per-row `lists_touch` logic was not exercised and is flagged as an open follow-up.
- **`FINDINGS.md` #20 (High)** — same file as #18: Patient Insurance's already-known destructive-overwrite `PUT` (`FINDINGS.md` #4) is materially worse under concurrency — of 5 concurrent single-field `PUT`s to one record, only the last writer's field survives, silently erasing every other concurrent caller's change with no error to anyone.
- **`FINDINGS.md` #19 (Medium)** — same file as #18: the already-known "reports success regardless of outcome" pattern on Message/Appointment (`FINDINGS.md` #1/#3) also produces a genuine concurrent lost-update race (only 6–7 of 10 concurrent message-body appends survive) and lets concurrent duplicate `DELETE`s of one appointment all report success identically.
- **`FINDINGS.md` #21 (Medium)** — same file as #18: Practitioner creates show the opposite failure mode from #18 — `users.username` has zero uniqueness guard at any layer, so concurrent duplicate-username creates always succeed, every time, no race window at all.

Two iteration snags worth remembering for future grey-area work, both already fixed: the Insurance test's first draft used a formulaic marker string for every raced field, which failed validation on `subscriber_state` specifically (constrained to a real state-code list) — fixed by using a real state code for that one field. The Practitioner test's first draft had no cleanup, and its leaked shared-username fixture rows permanently broke the pre-existing `UsersDbTests.Users_Table_Has_No_Duplicate_Populated_Usernames` test until a `finally`-block cleanup was added (caught by running the *full* suite after adding the new test, not just the new test in isolation — worth doing every time). ## Environment — How To Stand It Up

```
cd docker
docker compose up -d
docker compose ps
```

Wait for both `mariadb` and `openemr` to show `healthy` — first boot after a volume reset takes several minutes (schema install + Apache startup), not seconds, and the `openemr` container can report `unhealthy` for 2-6 minutes before flipping to `healthy`. This is normal (confirmed via container logs — it's still running its own setup script, not crashing); poll past the first `unhealthy` reading rather than treating it as a failure.

**No manual first-login browser steps are actually required before the test suites pass** — confirmed this session by reading `LoginPage.ts` (`loginAs()` already calls `dismissRegistrationModalIfPresent()`, which clicks "Ask again later" on the product-registration modal automatically) and by the fact that CI (`run-suite.yml`) has always started from a bare fresh `docker compose up -d` with zero manual steps and passed. `docker-compose.yml`'s `OPENEMR_SETTING_rest_api`/`OPENEMR_SETTING_rest_fhir_api`/`OPENEMR_SETTING_oauth_password_grant` env vars already cover the Administration → Config → Connectors settings a human would otherwise click through. `node docker/reset-env.mjs` resets to a fresh volume and polls to healthy — nothing further is needed before running the suites.

If exploring the app manually in a browser (`https://localhost:9300`, `admin`/`pass`) rather than running the automated suites, the product registration prompt will still appear on first login (dismiss it, no effect on tests either way).

Then:

```
cd ../tests
dotnet restore OpenEmr.Tests.sln
dotnet test OpenEmr.Tests.sln
```

For the UI layer:

```
cd ../ui
npm install
npx playwright install
npx playwright test
```

5. **Firefox-specific UI flakiness turned out to be (at least) two distinct, unrelated bugs, not one — both traced and one fully resolved, see `CONTEXT.md`'s decision-log entries below.** The investigation started from a much-worse-than-baseline full-suite run (4 failed/10 flaky out of 54) and confirmed via a freshly-`reset-env.mjs`'d, fully isolated, single-worker run that it wasn't resource contention or fixture buildup — `patient-portal.spec.ts` failed all 9/9 attempts on firefox alone with nothing else running. `CalendarPage.goto()`'s top-nav click was fixed with `{ force: true }`, confirmed 9/9. `DuplicatePatientsPage.goto()`'s `Admin`→`Patients`→`Manage Duplicates` chain turned out to be a genuinely different problem once diagnosed with a throwaway probe script: (1) `getByRole('button', {name:'Patients'})` returns zero matches on Firefox once the surrounding state changes (confirmed via direct DOM inspection that the exact element is present and visible the whole time — a real Firefox accessibility-tree gap), fixed by switching to the plain `.menuLabel`-text locator pattern already used everywhere else in this project; (2) a separate, still-not-root-caused Bootstrap nested-dropdown timing race where the submenu sometimes just doesn't open, mitigated (not eliminated) with a retry-until-visible loop. Verified via 11 repeated isolated trials across two batches: went from "usually hard-fails even after 2 retries" to "always eventually passes." `patient-portal.spec.ts`'s own remaining failure is a *third*, still-open, unrelated issue — the calendar day-view's plain `New Appointment` link hits the same "stable" actionability symptom `CalendarPage.goto()` had, but `{ force: true }` hasn't been tried there yet. A future session should try that next, and should assume any other `.menuLabel`/`.menuSection` click site elsewhere in this project (`BillingManagerPage`, `BillingPaymentPage`, `EncounterPage`, `PatientRegistrationPage`, `UserManagementPage`) could in principle hit either of these same two bug classes, verified independently rather than assumed fixed by association.
6. **The `{ force: true }` follow-up flagged in item 5 was attempted and did not work — the real problem sits one level upstream and is now much better understood, but still open.** Diagnosed live with a throwaway probe script (`MutationObserver`, `elementFromPoint`, direct DOM/CSS inspection of the calendar tab's container) rather than guessed at. The actual failure isn't the `New Appointment` link at all — it's that the top-nav `Calendar` label click itself already fails Firefox's "visible, enabled, stable" actionability wait in this specific test's flow (patient creation → demographics editing → portal-credentials modal → switch to Calendar), the identical signature `CalendarPage.goto()` already has a working fix for. But applying `{ force: true }` to the downstream click didn't help — worse, it masked the real symptom without fixing the real effect: even a forced click (tried twice in a row) never flips the Calendar tab's own wrapping container out of `display:none`, so the tab never actually becomes visible even though its iframe does reload real content in the background. Ruled out directly: stale/duplicate-element targeting (the correct, visible nav label is unambiguously what gets resolved and clicked), visual occlusion by the credentials modal the test manually tears down afterward (that teardown is confirmed working — `elementFromPoint` correctly stops resolving to the modal once it runs), and plain timing (a 10-second settle wait after teardown, before any click, made no difference — this is a stuck state, not a race that just needs patience). Leading, not-yet-confirmed theory: this app's Knockout.js-bound top nav (`data-bind="click: menuActionClick, css: {menuDisabled: ! enabled()}"`) has internal view-model state that this test's own necessary workaround — forcibly stripping the credentials modal's DOM nodes rather than triggering its real close path, since the modal doesn't reliably self-close within a few seconds either — never resets, even though the workaround does fully clean up the *visual* symptoms of "a modal is still open." See `CONTEXT.md`'s new decision-log entry for the full trail, and `ROADMAP.md` for the scoped-down follow-up session (test the Knockout `enabled()` theory directly, and/or try invoking the credentials modal's real close callback instead of stripping its DOM) now that this is understood well enough to test a specific theory instead of guessing at fixes.
